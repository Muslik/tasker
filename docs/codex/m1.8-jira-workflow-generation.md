# M1.8: Jira workflow generation

Status: implemented and verified 2026-08-02

Scope: turn one current Jira snapshot and one resolved managed checkout into an
inspectable, validated, persisted workflow. Execution remains disabled until M2.

## What determines the workflow

Workflow creation has two deliberately different parts.

The deterministic admission boundary verifies that the Jira snapshot is current and
the checkout is managed. It maps a Jira Bug to the conservative `short_bugfix` base
template, including reproduction, bounded implementation attempts, targeted
verification, PR preparation, and the code-review wait. Other issue types start from
`feature_with_review`. These defaults are not claims about the eventual solution.

The read-only analyzer receives:

- the complete persisted Jira snapshot: description, labels, comments, links, and
  attachment metadata;
- exact `project/repository` identity and managed checkout path;
- bounded repository file and workflow-document evidence collected by the provider;
- project/global workflow policies, registered step/wait contracts, capabilities, and
  the conservative base template.

The analyzer proposes task-specific assembly decisions, a workflow source graph, and
a verification plan. Its JSON is untrusted. The existing deterministic proposal parser,
compiler, capability validator, workflow validator, and template diff decide whether
the proposal can be persisted. The model never makes a graph executable by itself.

## Persistence and recovery

Jira intake history remains under `intake:jira:<key>`. Workflow analysis and planning
use `workflow:jira:<key>`, so workflow persistence cannot conflict with the earlier Jira
aggregate. The durable transaction stores the proposal, analyzer receipt, validator
report, template diff, compiled graph, and operator projections.

Opening or refreshing the task reads those projections; it does not rerun the analyzer.
Concurrent duplicate generation returns the first saved workflow. A Jira or Bitbucket
`403` before generation leaves the Jira snapshot and checkout intact. Once the workflow
is saved, a later VPN failure cannot remove it.

A rejected proposal is an attempt, not a terminal task. **Regenerate workflow** starts
another analyzer attempt from the same Jira snapshot and managed checkout. Rejected
events, validator reports, and provider receipts remain immutable; retry artifacts use
an `attempt-N` suffix while the current projections advance to the newly accepted or
rejected graph. A valid workflow stays idempotent and is never regenerated implicitly.

## Operator path

1. Import or open a Jira key and optionally supply a repository fallback.
2. Tasker synchronizes Jira and resolves/provisions the managed checkout.
3. The task shows `ready to generate workflow`; the right rail shows analysis ready.
4. Press **Generate workflow**.
5. Activity shows repository mapping, analyzer completion, and compilation; the right
   rail shows the persisted graph and the center explains every assembly decision.
6. If validation rejects it, fix the harness and press **Regenerate workflow**; Tasker
   reuses Jira and checkout state while retaining the rejected attempt.
7. Reloading restores the same graph without another provider call.

## Verification

- contract: Jira snapshot, comments, attachments, qualified repository identity, and
  managed checkout reach the analyzer request;
- contract: Jira intake and workflow events use separate aggregates;
- contract: rejected attempt -> regenerated valid graph preserves both attempts and
  versions the new artifacts;
- contract: deterministic Jira generation persists a valid graph and updates the queue;
- browser: import Jira, inspect details, generate, and see `reproduce-bug` in the graph;
- full repository suite: 108 tests;
- browser suite: 7 tests.

The live smoke run against Jira `AVIA-13236` and the managed
`onetwotrip/front-avia` checkout produced a valid graph with reproduction, a
three-attempt implementation loop, targeted plus visual verification, PR preparation,
and a slot-releasing code-review wait. The subscription analyzer completed in 59.1 s
with 58,798 measured tokens; its receipt and graph hash are persisted in the local
ledger. The preceding `AVIA-13235` smoke run exposed two rejected contracts (an
invented source envelope, then a missing step input). Those failures caused no remote
writes and directly led to the explicit workflow-envelope prompt and JSON input schemas
now supplied for every registered step. Regeneration then reused its persisted Jira
snapshot and managed checkout, retained the rejected validator evidence as attempt 1,
and accepted a valid visual-verification graph as attempt 2.
