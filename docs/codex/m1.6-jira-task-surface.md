# M1.6: persisted Jira task surface

> **Historical implementation record.** Jira product behavior remains relevant. Any
> custom ledger/outbox execution wording is superseded by the Temporal architecture.

Status: implemented and verified 2026-08-01

Scope: read-only Jira intake and operator presentation

## Operator contract

The `+` action in the left task queue accepts a Jira issue key. Tasker immediately
persists the intake identity, synchronizes a normalized issue snapshot, selects the
task, and shows:

- persisted activity in the center;
- compact task description, comments, links, and collapsed evidence below it;
- the real planning blocker and prerequisites on the right.

An imported Jira task is not workflow-ready merely because its description is
available. Until a target repository is mapped, the `Generate workflow` action is not
offered. This prevents the fixture repository or a guessed graph from masquerading as
real analysis.

## Data and failure flow

```text
issue key
  -> persist JiraIntakeRequested
  -> GET Jira issue (read-only)
  -> validate + normalize
  -> replace the current Jira projection in one transaction
  -> project task/activity/details
```

Synchronization is not activity. A successful refresh and a Jira access error update
the current projection (`status`, `recordedAt`, and `lastSuccessfulSyncAt`) without
appending an event, snapshot, or artifact. The details header shows the latest check
time. This keeps repeated manual refreshes from growing the operator log or ledger.

Every state is explicit:

- `current`: the latest Jira read succeeded;
- `stale`: a previous snapshot exists but the latest read failed;
- `unavailable`: the intake exists but no successful snapshot exists yet.

Jira `403` maps to retryable `access_blocked`. It normally means VPN or Jira access is
missing. The task remains in the ledger, a prior snapshot remains readable, and Retry
repeats only the synchronization step. Nothing restarts the task or discards prior
work.

`401` and `404` are non-retryable until credentials or the issue key change. Network
and server failures are retryable. Invalid Jira payloads fail at the Zod boundary and
are never persisted as successful snapshots.

## Attachments and credentials

The browser never receives the Jira token. It requests attachments through Tasker;
the server verifies that the Jira content URL has the configured origin, adds the
Bearer token, and limits a payload to 32 MiB.

Configuration resolution order:

1. `JIRA_BASE_URL` and `JIRA_TOKEN` from the Tasker process environment;
2. the same values from `${TASKER_HARNESS_WORK_PATH}/.env`;
3. when that path is not set, `../harness/work/.env` relative to the Tasker working
   directory.

No Jira write endpoint is implemented in this milestone. Editing status, assignment,
description, or comments must wait for the durable effect/outbox and reconciliation
contract; direct browser-to-Jira writes would violate recovery semantics.
