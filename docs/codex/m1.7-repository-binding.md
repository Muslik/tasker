# M1.7: Jira repository binding

Status: implemented and verified 2026-08-02

Scope: resolve one Jira task to one logical local repository without guessing from
the Jira project.

## Resolution contract

Tasker resolves repository identity in this order:

1. an exact line in the Jira description: `repo:front-avia`;
2. the optional repository supplied in the Tasker import form;
3. no match: the task remains blocked and the analyzer is not started.

The Jira directive wins over the import fallback. A fallback is persisted and reused
by later header Sync actions, so a refresh does not lose the mapping. Multiple
different `repo:` lines, an unknown name, or multiple matching remotes are explicit
blocked states. Jira project keys are never treated as repository names because the
same repository can serve several Jira projects.

`JiraRepositoryReferenceSource` is the replacement boundary for a future custom Jira
field. Switching source does not change catalog lookup, persistence, or the analyzer
contract.

## Local catalog

At startup Tasker scans immediate git checkouts under `TASKER_REPOSITORY_ROOTS`. The
value uses the platform path delimiter and defaults to `../work`, which resolves to
`/Users/dzhabrail/Projects/work` in the current setup. `TASKER_RUNNER_ID` identifies
the machine and defaults to `local`.

Checkouts with the same normalized `origin` URL are one logical repository. For the
known `front-avia` and `front-avia-2` clones, the exact `front-avia` directory is the
preferred checkout and both paths remain visible in catalog evidence. Equal names
from different remotes are ambiguous rather than chosen by path order.

## Persistence and operator activity

The current Jira snapshot and repository binding are durable projections. Only the
initial import and a changed repository binding are activity-worthy ledger events.
Jira refresh success, `403`, and unchanged repository state create no events,
snapshots, or artifacts. The current sync/check time is displayed beside `Jira
synced` or `Cached` in Task details.

This distinction keeps the operator surface useful:

- center Activity: decisions and state changes;
- Task details: current Jira state and the time it was checked;
- ledger projection: the latest recoverable cached Jira payload;
- right rail: repository resolved/blocked, then analyzer and compiler prerequisites.

## Current boundary

This slice stops after repository resolution. A resolved task is back in the backlog,
but its planning status remains blocked with `Jira analyzer pending`. The next slice
must invoke the existing read-only analyzer against the resolved checkout and compile
its proposal; it must not synthesize a workflow from Jira text alone.
