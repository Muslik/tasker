## Goal

Построить локальный harness, который принимает рабочую задачу из Jira и доводит её до **pull request с разобранными комментами ревью**, при этом:

- собирает под каждую задачу граф из библиотеки типовых шагов (не один фиксированный сценарий и не ручная сборка человеком);
- исполняет шаги подписочными CLI-агентами (claude / codex / antigravity), не потокенным API;
- показывает **стоимость в долларах и длительность каждого шага и каждой попытки**, с суммой по группе;
- позволяет человеку вмешаться между шагами — в первую очередь отредактировать промпт следующего шага до его запуска;
- завершает прогон шагом ретроспективы, который пополняет проектное знание и предлагает правки промптов и графа.

Режим работы, выбранный пользователем: **фабрика**. Человек — диспетчер, ставит 5–10 задач в очередь и трогает систему в двух точках: апрув плана и мёрдж PR. Главная метрика — пропускная способность.

---

## Constraints

1. **Подписка, не потокенная оплата.** При упоре в лимит прогон уходит в паузу. Пауза обязана переживать перезапуск процесса; человек может либо продолжить с того же места, либо забрать задачу и доделать руками.
2. **Workspace прогона — обычный git worktree.** Не одноразовый контейнер: человек должен иметь возможность сесть в эту директорию и дописать задачу руками. Существующий инструмент `wt` (`~/dotfiles/bin/wt`, хук `~/.config/wt/post-create` → `harness/bin/harness-wt-hook`) — естественная точка интеграции.
3. **Права агента: всё до мёрджа.** Создаёт ветку, пушит, открывает PR, триггерит бота-ревьюера, отвечает в тредах, пушит фиксы. Мёрдж и закрытие задачи — всегда человек.
4. **v1 исполняется только локально.** Граница «оркестратор ↔ воркер» должна быть проведена так, чтобы вынос воркеров на VPS позже был переездом, а не переписыванием.
5. **Промпты и граф — версионируемые артефакты** с историей и возможностью отката. Ретроспектива предлагает к ним дифф, человек апрувит.
6. **Целевой параллелизм 5–10 прогонов**; фактический ограничен лимитами подписок и определяется опытно.
7. **Ограниченные повторы.** Циклы имеют собственный потолок попыток (`loop N/M`) и явные ветки капитуляции, которые оставляют коммент вместо тихого зависания.
8. **Стек интеграций фиксирован:** Jira, Confluence, Bitbucket, Jenkins + Allure, Loop (Mattermost).

## Non-Goals

Явно исключено пользователем или отложено:

- **Эталонный набор задач, грейдер, регресс-прогон эвалов.** Исключено на R6 после разбора цены и способа реализации. Проверка правок промптов — по тренду метрик реальных прогонов плюс версионирование и откат. Принятый риск: постепенная деградация от накопления правок не будет обнаружена формальным способом.
- **Режим record/replay у адаптеров интеграций.** Следствие предыдущего пункта: без эвалов не нужен.
- **Автоматический мёрдж PR и перевод задачи в Done.**
- **Исполнение на VPS в v1.**
- **Ручная сборка графа человеком.** Явно отвергнуто на R8.
- **Отдельный флоу для переводов.** Разобрано на R0: это экземпляр общего примитива `await`, а не самостоятельный сценарий.

## Acceptance Criteria

### Фаза 1 — v1, выбрана пользователем: ядро + очередь, шаги-заглушки

- [ ] Движок исполняет граф из типовых шагов; поддержаны `loop N/M` (ограниченный повтор со счётчиком попыток) и вложенный `when` (условные ветки)
- [ ] Прогон переживает перезапуск процесса: остановка и повторный старт продолжают с того же шага, без потери состояния
- [ ] Тип шага `await` блокирует ветку до внешнего сигнала; первый источник сигнала — кнопка в UI
- [ ] Очередь со слотами; при упоре в лимит подписки прогон уходит в паузу, а не падает
- [ ] Каждый шаг и **каждая попытка внутри цикла** пишут стоимость и длительность; на группе показывается сумма
- [ ] UI показывает дерево воркфлоу со статусами, живой транскрипт активного шага, бейджи `$` и времени, реплей транскрипта завершённого шага по клику
- [ ] Человек может отредактировать промпт следующего шага до его запуска
- [ ] Прогон пишет в лог: base SHA, снапшот текста задачи, весь tool-I/O, финальный дифф
- [ ] Workspace прогона — git worktree, пригодный для ручного подхвата человеком
- [ ] Прогон можно поставить на паузу, снять с паузы, перезапустить отдельный шаг и отменить целиком

### Фаза 2 — реальные шаги и интеграции

- [ ] Библиотека типов шагов наполнена реальными реализациями поверх существующих скиллов (`investigate-bug`, `fix-bug`, `reproduce`, `review-process`, `pr-finalize`)
- [ ] Адаптер Jira: чтение задачи, комменты, переходы статусов
- [ ] Адаптер Bitbucket: ветка, пуш, создание PR, чтение и ответ в тредах ревью
- [ ] Адаптер Jenkins + Allure: триггер сборки, чтение результата, извлечение упавших тестов и вложений
- [ ] Адаптер Loop: чтение тредов, пост в канал; используется как источник сигнала для `await`
- [ ] Триггер бота-ревьюера и цикл разбора его замечаний
- [ ] Один тип задачи (баг) проходит путь конец в конец: Jira → repro → fix → PR → цикл ревью → готово
- [ ] Скрипт `sync-translations` работает независимо от харнесса

### Фаза 3 — ретроспектива и автономность

- [ ] Шаг `retrospective` — узел графа, исполняемый в конце прогона
- [ ] Выход 1: отчёт человеку — где встало, сколько стоило, какие шаги оказались лишними, где человек вмешивался
- [ ] Выход 2: дифф к промпту или графу, предлагаемый системой и апрувимый человеком как PR
- [ ] Выход 3: проектное знание, записываемое в `.ai/` профиля и подмешиваемое в последующие прогоны
- [ ] Метрики для тренда: доля шагов без вмешательства, стоимость прогона, число итераций ревью, доля прогонов дошедших до PR
- [ ] Аналитик собирает граф: шаблон по типу задачи + правки под специфику + видимый человеку дифф от шаблона
- [ ] Точки апрува конфигурируемы: план ревьюится или нет, PR ревьюится или нет

### AC-R — компонент `research`

- [ ] Составлен обзор кандидатных инструментов по четырём осям: движок долгоживущих процессов, оркестрация агентов, наблюдаемость LLM-прогонов, готовые UI для агентных задач
- [ ] По каждому кандидату зафиксировано: покрывает ли durable-паузу, даёт ли per-step стоимость, работает ли с CLI-агентами по подписке, лицензия
- [ ] Принято и обосновано решение build-vs-buy по каждому из семи компонентов
- [ ] Обзор содержит явную отметку, что проверено на практике, а что взято из документации

### Модель графа (вычитана из референсной реализации)

- **Узел** = `имя · тип шага`. Один тип переиспользуется под разными именами и контекстами: `verify` встречается как `verify`, `predictive-verify`, `verify-ci-fix`, `predictive-verify-ci`
- **Типы шагов, наблюдённые в референсе (~21):** `issue-reproduce`, `ralplan`, `plan`, `reproduce-fixture`, `visual-reproduce-before`, `implement`, `plan-conformance`, `verify`, `visual-reproduce-after`, `comment-lint`, `finalize`, `local-duo-review`, `process-duo-review`, `implement-duo-review-suggestions`, `push-mr-update`, `undraft-mr`, `run-ci`, `analyze-ci-failure`, `implement-ci-fix`, `post-ci-comment`, `retrospective`
- **`loop N/M`** — ограниченный повтор: текущая попытка из максимума. Стоимость агрегируется суммой по группе
- **`when`** — вложенные условные ветки. CI-хвост построен как дерево решений с явными ветками капитуляции: `post-ci-not-ours`, `post-ci-blocked`, `post-ci-gaveup`
- **Учёт стоимости на трёх уровнях:** узел, отдельная попытка внутри цикла, сумма по группе
- **`retrospective` — терминальный узел графа**, а не внешний процесс

### Направления поиска для фазы research

Кандидаты названы по памяти и **подлежат проверке** — версии, лицензии и фактические возможности необходимо подтвердить перед выбором.

| Ось | Кандидаты к проверке | Что именно проверять |
|---|---|---|
| Долгоживущие процессы | Temporal, Restate, Inngest, DBOS | Переживает ли пауза на часы и перезапуск процесса; вес зависимости для одного пользователя |
| Оркестрация агентов | LangGraph, Claude Agent SDK, OpenAI Agents SDK | Ложится ли модель `loop N/M` + вложенный `when`; можно ли драйвить внешние CLI, а не только API |
| Наблюдаемость LLM | OpenTelemetry GenAI semantic conventions, Langfuse, Phoenix/Arize, Braintrust, W&B Weave | Есть ли стоимость по шагу и попытке; можно ли считать $ для подписочных CLI, где токены не тарифицируются напрямую |
| Готовые UI агентных задач | Conductor, Sculptor, Terragon, Vibe Kanban, сам Cockpit | Открыт ли исходный код; отделим ли UI от их движка |
| Кодовые агенты как шаги | OpenHands, SWE-agent, Aider | Пригодны ли как реализация отдельного типа шага |

Отдельный вопрос для research: **как получить стоимость в долларах для подписочных CLI**. Прямой тарификации нет; вероятный путь — считать токены из транскрипта и умножать на публичные цены соответствующей модели, что даёт «эквивалентную стоимость», а не фактический счёт. Формулировку в UI надо подобрать так, чтобы это не читалось как реальные списания.

Не блокируют планирование, но требуют решения при исполнении:

1. **MCP `onetwotrip` возвращает «Доступ к проекту Jira AVIA запрещён»** для `AVIA-13236`, `AVIA-13235`, `AVIA-12536`. Нужен либо другой токен, либо путь через REST-скилл `jira` из `harness/global/skills`. Проверить до того, как интеграция Jira попадёт в план.
2. **`app-runbook.md` есть только в `front-avia`.** Скилл `reproduce` опирается на эту карту dev-окружения (dev-сервер, логин, deep-links, моки API). Для остальных шести репозиториев автоматическое воспроизведение бага сейчас не на что опереть.
3. **DoD для research/investigate-задач не определён.** Допущение: результат — комментарий в Jira или страница в Confluence с выводом и ссылками; критерий прохождения — человек апрувит. Требует подтверждения.
4. ~~**Как считать стоимость в долларах на подписке.**~~ **Закрыто research'ем** — см. [research-landscape.md](research-landscape.md), раздел 3. Claude Code отдаёт `total_cost_usd` готовым; Codex и Antigravity — только токены, доллары считаются самим харнессом по прайс-таблице. Формулировка для UI: «оценочная стоимость по стандартным ценам API — не фактическое списание».
5. **Распределение шагов по провайдерам.** Какие шаги на claude, какие на codex, какие на antigravity — не обсуждалось.
6. **Скоуп репозиториев для фазы 2.** Обсуждался `front-avia` как первый; про остальные шесть решения нет.
7. **Antigravity как исполнитель шага под вопросом.** Открытый баг: `agy --print/-p` теряет stdout при запуске из non-TTY контекста, то есть ровно из подпроцесса. Требует практической проверки до включения в v1.
8. **Остаток квоты подписки не читается программно ни у одного CLI.** Следствие для `engine`: шедулер не может делать preflight-проверку перед запуском шага — упор в лимит детектируется только по ошибке постфактум. Меняет реализацию требования «пауза при лимите».
