# Research: ландшафт инструментов для agent-harness

Сопровождает [spec.md](spec.md), закрывает критерии AC-R.
Дата: 2026-07-30. Метод: 5 параллельных агентов-исследователей, ~360 веб-запросов.

**Как читать.** Источники размечены агентами как `[ОФИЦ]` (официальная документация, прочитана напрямую), `[ВТОР]` (блог, агрегатор, сниппет поиска) и `[НЕ ПОДТВ]`. Разметка сохранена. Всё, что помечено не как `[ОФИЦ]`, требует проверки до того, как на этом строить решение.

## Главные выводы, в порядке практической важности

### 1. Cockpit публично не существует — и он построен на том же OMC, что стоит у вас

Целенаправленный поиск не нашёл продукта с описанными признаками. Ключевые проверки:
- GitHub repo-search по `"issue-reproduce" "ralplan"` → **0 результатов** (прямая проверка).
- Поиск по `"Cockpit" GitLab workflow tree cost badge` и вариациям → совпадений нет.
- Три существующих проекта с именем Cockpit (`enriquekalven/agent-cockpit`, `Surething-io/cockpit`, `cth9191/agentic-os-dashboard`) — ни один не подходит по описанию.

**Но найдена природа названия шага `plan · ralplan`:** `ralplan` — это не отраслевой термин, а **имя скилла из oh-my-claudecode** — той самой системы, что установлена у вас (`ralplan` есть в вашем списке скиллов). Источник: `github.com/Yeachan-Heo/oh-my-claudecode`, `github.com/Yeachan-Heo/oh-my-codex/blob/main/skills/ralplan/SKILL.md`.

Отсюда рабочая гипотеза (гипотеза, не факт): Cockpit — приватная обвязка поверх OMC, где шаг пайплайна буквально вызывает OMC-скилл. Практический вывод для вас двоякий: готовый код взять неоткуда, **но** библиотека шагов у вас уже частично есть — в виде тех же OMC-скиллов и ваших собственных из `harness/`.

### 2. Ни один существующий инструмент не закрывает задачу целиком

Проверено ~23 инструмента. Ближе всего по отдельным осям:

| Ось | Кто ближе всех | Чего не хватает |
|---|---|---|
| Явный граф с ветвлением и циклами | **Bernstein** (Apache-2.0, YAML DAG, 40+ CLI-агентов) | cost/time-UI не подтверждён (403/429 на доках), проект маленький и молодой |
| Очередь + worktree + мультипровайдер + отделимый UI | **Vibe Kanban** (Apache-2.0, 10+ агентов, frontend/backend разделены) | граф плоский — канбан-колонки, не DAG; стоимости нет вообще |
| Интейк задач из трекера → worktree → агент | **Cyrus** (Apache-2.0, единственный с подтверждённым GitLab) | один сквозной поток issue→MR, без многошагового графа |
| Реальный cost/time в UI | только закрытые коммерческие (Cursor, Devin через ACU) | исходники недоступны |
| Изоляция как отдельный слой | **container-use** от Dagger (Apache-2.0) | нулевой UI, только CLI/MCP |

**Что придётся написать в любом случае, чего нет нигде:**
1. Компилятор «тип задачи из трекера → именованный граф шагов».
2. UI «дерево воркфлоу с бейджами $ и времени **на каждом узле**» — этой комбинации не нашлось нигде в подтверждённом виде.
3. Глобальный лимит слотов поверх множества одновременных многошаговых графов (везде только «N параллельных независимых задач»).
4. Живой транскрипт по шагу как первоклассная фича.

### 3. Стоимость на подписке: что реально достижимо

Самый конкретный результат исследования.

| CLI | Машиночитаемый режим | Токены | Доллары | Остаток квоты |
|---|---|---|---|---|
| **Claude Code** | `claude -p --output-format json\|stream-json` | да | **да, готовые** — `total_cost_usd`, `modelUsage[].cost_usd` | `/usage` — **только интерактивный TUI** |
| **Codex CLI** | `codex exec --json` (JSONL) | да, `turn.completed.usage` | **нет** — считать самим | `/status` — только TUI, есть открытый feature request |
| **Antigravity** | `agy -p --output-format json` | да | **нет** — считать самим | `/usage` — только TUI, но дёргает реальный бэкенд |
| **Gemini CLI** | `gemini -p --output-format json` | да, `stats` | нет | `/stats` — только токены сессии |

**Три вывода, каждый влияет на дизайн:**

**(а) Остаток квоты не читается программно ни у кого.** Ни один CLI не отдаёт «сколько осталось» вне интерактивной панели. Значит **шедулер не может делать preflight-проверку перед запуском шага** — он обязан детектировать упор в лимит по ошибке постфактум и реагировать. Это прямо меняет реализацию требования «пауза при лимите» из спеки.

**(б) Честная формулировка для UI.** Официальная документация Claude Code дословно: *«Claude Max and Pro subscribers have usage included in their subscription, so the session cost figure isn't relevant for billing purposes»* и *«computes the dollar figure locally from token counts priced at standard list rates… may differ from your actual bill»* `[ОФИЦ]`. ccusage формулирует так же: *«an API-equivalent estimate, not a ChatGPT credit balance»* `[ОФИЦ]`.
Рекомендуемая формулировка: **«оценочная стоимость по стандартным ценам API — не фактическое списание»**. Не использовать «потрачено», «списано», «сэкономлено» — так не формулирует ни один изученный инструмент.

**(в) Референсная реализация подсчёта есть и она открыта.** `ccusage` (`github.com/ryoppippi/ccusage`) читает локальные лог-файлы CLI и умножает токены на публичный прайс из датасета LiteLLM. Поддерживает Claude Code, Codex, OpenCode, Gemini CLI, Copilot CLI и др. Логику маппинга цен можно переиспользовать как референс. Известные баги точности: расхождение имён полей между источниками (issue 831), переучёт токенов Codex-сабагентов (issue 950).

### 4. Claude Code пробрасывает trace-context в подпроцесс — это бесплатная глубина наблюдаемости

`[ОФИЦ]` При наличии активного OTEL-спана у вызывающего приложения в дочерний процесс инжектится `TRACEPARENT`/`TRACESTATE`, и внутренний спан `claude_code.interaction` становится **дочерним спаном вашего харнесса**. Дальше дерево само разворачивается: `claude_code.interaction` → `claude_code.llm_request` / `claude_code.tool` / `claude_code.hook`, а сабагенты через Task-tool вкладываются под родительский `claude_code.tool`.

**Важная оговорка:** работает только для Agent SDK и `claude -p` — интерактивные сессии входящий TRACEPARENT игнорируют. Для харнесса это ровно нужный режим. Трейсинг помечен вендором как **beta**: «Span names and attributes may change between releases».

Для Codex картина беднее: OTEL есть в конфиге (`[otel]` в `~/.codex/config.toml`), но `codex exec` — то есть именно неинтерактивный режим — **не эмитит метрики вообще**, только logs/traces (issue 12913, закрыт с неясным исходом). Долларов там нет ни в каком виде.

### 5. Стандартного атрибута стоимости в OTEL не существует

`[ОФИЦ]` Прямая проверка реестра `opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/`: **атрибута цены нет**, только счётчики токенов. Весь namespace `gen_ai.*` в статусе Development, стабильного 1.0 нет. В июне 2026 (v1.42.0) контент был **вынесен из основного репозитория** в отдельный `semantic-conventions-genai`, канонические страницы на сайте сейчас показывают заглушку о переезде.

Встречающиеся упоминания `gen_ai.usage.cost_usd` — это расширения конкретных вендоров или выдумка авторов блогов, не стандарт.

Практически: **не закладываться на OTEL GenAI как на стабильный контракт**, и в парсере не хардкодить одно написание имён токен-атрибутов — экосистема сама признаёт, что разные интеграции шлют разные поколения атрибутов одновременно.

### 6. Antigravity под вопросом как исполнитель шага

Найден открытый баг в официальном репозитории: **`agy --print/-p` теряет stdout при запуске из non-TTY контекста** — то есть из пайпа, редиректа или подпроцесса (`github.com/google-antigravity/antigravity-cli/issues/76`). Это ровно тот сценарий, в котором харнесс будет его запускать.

Отдельно: два агента разошлись в том, заменил ли Antigravity CLI собой Gemini CLI. Один нашёл утверждение об отключении Gemini CLI 18.06.2026 `[ВТОР]`, другой оценил это как вероятную ошибку блога и считает продукты параллельными `[НЕ ПОДТВ]`. Конфликт не разрешён — проверять отдельно.

**Вывод: до интеграции Antigravity нужен практический тест «запусти из подпроцесса и прочитай stdout».** Если баг воспроизводится — Antigravity выпадает из v1 как исполнитель.

## Ось A: движки долгоживущих процессов

Полная таблица из 17 кандидатов — в приложении. Реалистичные для одного пользователя локально:

| Кандидат | Durable-пауза | Вес | Лицензия |
|---|---|---|---|
| **DBOS** | `DBOS.recv()`/`send()`, чекпойнт по шагам в Postgres; офиц. блог про HITL-апрувы | Библиотека, не демон — но **Postgres обязателен** для Python/TS (SQLite только в Go-SDK) | MIT |
| **Restate** | Awakeables — «survive retries and process restarts» `[ОФИЦ]`; есть офиц. страница «Durable Agents» | **Один Rust-бинарник, без внешней БД** — самый лёгкий | BUSL-1.1 → Apache через 4 года; личное и внутреннее использование свободно |
| **Temporal** | Signals + `wait_condition`, офиц. AI-кукбук по HITL, ожидание «at zero compute cost» | `start-dev --db-filename` даёт персистентный SQLite, **но** отдельная страница доков говорит «suitable for testing and development only» — противоречие в самой документации | MIT |

Отбраковано и почему: Netflix Conductor, Cadence, Windmill, Trigger.dev (тяжёлый стек сервисов), Camunda 8 (лицензия), Azure Durable Functions (облако), Dagster (нет примитива паузы посреди прогона — sensors запускают **новый** ран), Flowable/Camunda 7 (Java-only), Obelisk (pre-release + AGPL), Resonate (нет признаков зрелости).

Показательное наблюдение: **у всех зрелых durable-движков уже есть официальный AI-agent-паттерн** — Temporal, Restate, Inngest, DBOS, Hatchet. Индустрия сошлась на «взять универсальный durable execution + добавить сигнал для человека», а не строить отдельный класс движков под агентов.

Но все эти паттерны рассчитаны на оркестрацию **прямых вызовов LLM API** внутри workflow-кода. Готового рецепта под «шаг = запуск подписочного CLI как подпроцесса» не нашлось ни в одном официальном источнике.

## Ось B: фреймворки оркестрации агентов

**Вывод исследователя: ни один не спроектирован под «шаг = внешний CLI-подпроцесс».** Везде это «просто функция, которая попутно может дёрнуть subprocess» — то есть этот критерий вообще не различает фреймворки и не должен определять выбор.

Существенные детали по главным кандидатам:

- **LangGraph** (MIT ядро) — самая проработанная персистентность: checkpointer + `interrupt()`/`Command(resume=...)` переживают рестарт по `thread_id`. **Архитектурная ловушка для вашего кейса:** при resume LangGraph перезапускает узел **с начала**, а не с точки interrupt. Если вызов `claude`/`codex` стоит до `interrupt()` в одном узле, он выполнится повторно при каждом resume. Для шага, который стоит 5 минут и реальных денег, это дорого. Обходится разнесением по узлам, но это уже борьба с фреймворком. Граф статичен — компилируется один раз.
- **Claude Agent SDK** — это **не движок, а то, что движок будет вызывать**: сам является обёрткой, запускающей `claude` CLI как подпроцесс. Ни узлов, ни рёбер, ни ветвления. Лицензия — Anthropic Commercial ToS, не OSS.
- **Google ADK 2.0** (Apache-2.0) — ближе всех к «динамическому графу»: graph-based workflows с decision branching и dynamic workflows на чистом коде появились в мае–июне 2026. Слишком свежо, зрелость не подтверждена.
- **Burr / pydantic_graph** — самые лёгкие, узел = обычная функция без навязанной агентной онтологии. Но HITL и durable resume — не первоклассные примитивы. Показательно: pydantic_graph официально рекомендует для настоящей durability **прицепить снаружи Temporal/DBOS/Prefect/Restate** — то есть сам признаёт, что не решает эту задачу.

**Прямой прецедент от Anthropic.** Блог команды Claude Code «A harness for every task: dynamic workflows in Claude Code» описывает ровно вашу проблему — динамическая сборка harness под задачу, координация сабагентов, устойчивость к прерыванию. Их решение — **не внешний граф-фреймворк, а маленький кастомный JS-DSL**: workflow это JS-файл с несколькими специальными функциями, который Claude пишет на лету под задачу; при прерывании повторный запуск сессии продолжает с той же точки.

## Ось C: наблюдаемость

Если брать готовое — два кандидата:

- **Arize Phoenix** — самый лёгкий физически: `pip install arize-phoenix && phoenix serve`, SQLite под капотом. Чистый OTLP-коллектор, принимает любые спаны. Cost-tracking с rollup до trace и project. Elastic License 2.0 (source-available, self-host бесплатен без ограничений).
- **Langfuse** — зрелее по UI и cost-логике, нативный OTLP-эндпоинт, MIT почти целиком. Цена — 5-6 контейнеров: Postgres + ClickHouse + Redis + S3-совместимое хранилище.

**Но рекомендация исследователя — своя таблица событий как система правды.** Причины конкретные:
1. **«Попытка» (attempt) в цикле retry — не родное понятие ни для OTEL, ни для одного бэкенда.** Моделируется как дочерний спан, но готового UI «попытка N из M, сравнить с предыдущей» нет нигде. А у вас это требование первого уровня — на скринах Cockpit два бейджа стоимости на одном узле.
2. **Живой транскрипт «прямо сейчас, пока шаг выполняется» — не сильная сторона ни одного трейс-эксплорера.** Они спроектированы как post-hoc: спан появляется после ingestion, у Claude Code трейсы батчатся с интервалом 5 секунд по умолчанию. Живой пейн придётся кормить напрямую из stdout.
3. **Только один из трёх агентов отдаёт богатую телеметрию.** Нормализующий слой в харнессе обязателен в любом случае.

## Решения build-vs-buy по компонентам

| Компонент | Решение | Обоснование |
|---|---|---|
| `engine` | **Писать своё** — тонкий интерпретатор графа поверх append-only JSONL-журнала | `loop N/M` с капитуляцией не является примитивом нигде — пишется руками поверх любого движка. Гранулярность чекпоинта здесь «шаг = один subprocess-вызов», это радикально проще того, что решают Temporal/LangGraph. Прямой прецедент — команда Claude Code выбрала мини-DSL, а не фреймворк |
| `engine`, durable-слой | **Не брать в v1.** Путь эскалации — Temporal, если понадобится | Пауза между шагами покрывается журналом. Temporal решает крах **посреди** активности — для локального однопользовательского инструмента это цена без выгоды. Если требования вырастут: workflow-код становится интерпретатором, каждый CLI-вызов — одной Activity |
| `runtime` | **Писать адаптеры**, но сначала прочитать чужие | Адаптерный слой к CLI независимо реализован в Bernstein, Vibe Kanban, Claude Squad, Emdash, Cyrus — все Apache/MIT. Сравнить перед тем, как писать своё |
| `runtime`, изоляция | **Обычные git worktree через существующий `wt`** | Контейнеры (container-use, Sculptor) противоречат вашему требованию «человек садится и доделывает руками». У вас уже есть `wt` + post-create хук |
| `observability` | **Своя таблица событий как система правды** + опционально зеркалить в Phoenix | «Попытка» и живой транскрипт не покрываются готовым. Phoenix ставится одной командой — брать как бонусный трейс-эксплорер для отладки, не как замену |
| `observability`, стоимость | **Считать самим по прайс-таблице**, у Claude Code брать готовое число | Стандарта нет, остаток квоты не читается. Референс маппинга цен — ccusage (открытый) |
| `control` | **Писать своё** | Правки промпта на шаге, апрув-гейты и лимит слотов поверх многошаговых графов не покрыты нигде |
| `integrations` | **Поверх существующих скиллов** | `jira`, `bitbucket`, `jenkins`, `confluence`, `loop` уже есть в `harness/global` |
| `retro` | **Писать своё** | Терминальный узел графа, специфичен для вашего процесса |

**Что взять готовым по факту: почти ничего как зависимость, но многое как референс кода.** Это не отрицательный результат — это означает, что задача действительно новая, а не изобретение велосипеда.

**Чужой код, который стоит прочитать до начала:**
- Адаптеры CLI → `Bernstein`, `Vibe Kanban`, `Cyrus` (все permissive)
- YAML DAG с ветвлением и циклами → `Bernstein`, единственный прецедент для CLI-агентов
- Интейк «issue → worktree → агент» → `Cyrus`
- Фронтенд дерева задач с инлайн-ревью диффов → `Vibe Kanban`
- Подсчёт стоимости по токенам → `ccusage`

## Что обязательно проверить руками до начала реализации

Практические проверки, которые research закрыть не может:

1. **`agy -p` из подпроцесса** — воспроизводится ли потеря stdout (issue 76). Определяет, входит ли Antigravity в v1.
2. **Пережитие рестарта у выбранного варианта персистентности** — убить процесс посреди ожидания, поднять, проверить продолжение с той же точки.
3. **`claude -p --output-format stream-json`** — что реально приходит в `result`-событии на вашей версии. Плюс известный баг завышения `total_cost_usd` примерно в 10 раз (issue 53371) — проверить, актуален ли.
4. **TRACEPARENT-проброс в `claude -p`** — работает ли на практике, раз трейсинг помечен beta.
5. **Bernstein локально** — единственное белое пятно, которое решает «брать за основу или нет»: есть ли там cost/time и HITL. Доки отдавали 403/429.
6. **Доступ к проекту AVIA** — MCP `onetwotrip` отказывает; проверить REST-путь через скилл `jira`.

## Приложение: конкретика команд

```bash
# Claude Code — единственный, кто отдаёт готовые доллары
claude -p "prompt" --output-format stream-json --verbose --include-partial-messages
# result-событие: total_cost_usd, duration_ms, duration_api_ms, num_turns,
#   usage.{input,output,cache_creation,cache_read}_tokens, modelUsage[model].cost_usd
# сессии: ~/.claude/projects/<url-encoded-path>/<session-id>.jsonl
# OTEL: CLAUDE_CODE_ENABLE_TELEMETRY=1 → claude_code.cost.usage, claude_code.token.usage

# Codex — токены есть, долларов нет
codex exec --json "task"
```
