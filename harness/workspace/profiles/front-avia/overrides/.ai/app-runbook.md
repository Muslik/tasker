# front-avia — app runbook (how to run and drive the app locally)

The single source for "how do I start this app, log in, and reach page X".
Read by any block that needs a LIVE app (demo recording, bug reproduction,
visual verification). Don't reverse-engineer the setup — it's written here.

## Start the dev server

- Deps are already installed at worktree prep (`pnpm install --frozen-lockfile` + `pnpm run dicts`).
- Dev server: `pnpm start` (re-runs dicts, then rspack dev server). Background it.
- Base URL: **`https://local.onetwotrip.com:3004`** (host/port set in `.bundlerrc.mjs`;
  override via env `HOST`/`PORT`). `local.onetwotrip.com` must resolve to 127.0.0.1
  (present in /etc/hosts on the host machine; a container needs the same mapping).
- HTTPS with a local self-signed cert → in Playwright use `ignoreHTTPSErrors: true`
  (their own spec config does). Alternative: `pnpm run start:unsecure` → plain http.
- Ready signal: poll the base URL until it responds (first rspack build takes minutes —
  poll, don't sleep blind). Reuse a server that's already listening on :3004.

## API / stands

- Dev server PROXIES `/api` and all `/_*` paths to **prod** `https://www.onetwotrip.com`
  by default. Variants: `pnpm run start:beta` (beta-01 stand) / `start:sandbox` (sandbox-03).
- So "local" UI runs against real prod data — searches are real, and the test account
  lives there.

## Login (test account)

- Test account (Статус PRO): login in env `APP_USER`, password in env `APP_PASS`
  (set in minions `.env`, passed host-side; never hardcode).
- Flow: auth modal (shared `@ott/auth` SigninForm), opened from the header's login
  entry. The app's test-id attribute is **`data-locator`** (not data-testid).
  Form locators: `[data-locator="SigninForm--email"]`, `[data-locator="SigninForm--pwd"]`,
  submit — discover within `[data-locator="SigninForm"]`.
- A captcha limiter (`auth-enter`) exists but does NOT fire by default — automated
  login with this account just works. Still log in ONCE in the non-recorded context
  and reuse `storageState` (the demo template already does the split); if captcha
  ever does appear, say so in your output — don't fight it.

## Reaching app states (the state map — READ THIS BEFORE NAVIGATING)

**Policy, in order of preference:**

1. **Deep-link** — when the state lives in the URL (search). Fast, reliable.
2. **Deep-link + API mocks** — for DEEP states (pay / order / refund). This is how the
   project's OWN Playwright tests reach them: they never walk the live funnel — they
   `page.route` the API with fixtures from `spec/mocks/responses/<page>/` and open the
   page directly (see `spec/tests/logic/payment/*`, `spec/fixtures/mocker.ts`). Do the
   same unless the task is about the funnel itself.
3. **Live walk** — only when the scenario explicitly needs the real flow (e.g. the repro
   steps ARE the story). Use the state notes below; budget it — a live walk to pay takes
   minutes, not seconds.

**Selectors: the source of truth is `spec/pages/*.ts`** (test-id attribute is
`data-locator`). NOTE: page-object methods wrap `test.step`, so they only run inside
`pnpm exec playwright test` — from a plain script, MIRROR their selectors and action
order instead of importing them. Mock fixtures are TS modules — load them via
`ts-node/register/transpile-only` or copy the JSON payload.

**Probing rule: if an action fails twice, STOP guessing.** Do not coordinate-click. Find
how the project's own tests perform this exact step (`rg <action> spec/tests spec/pages`)
and copy it. Screenshots are for VERIFYING a step landed, not for discovering the UI.

### States (авиа)

- **Поиск (serp)** — deep-link `/ru/f/search/<pathname>`; pathname = `DDMM` + IATA-origin
  + IATA-dest, e.g. `1901MOWLED`, `2006DXBIST` (real examples in `spec/tests/`); date must
  be in the future. No auth or fixtures needed — real prod search. Page object:
  `spec/pages/searchPage.ts`. Главная (форма поиска): `/ru/f/index/`.
- **Бронирование (book)** — live from serp: clicking a flight card opens a DETAILS MODAL —
  the transition is the **«Выбрать» button INSIDE the modal** (the card click alone does
  NOT navigate). Lands on `/ru/f/book/<hash>`; the hash is generated by the selection, you
  can't fabricate it. Page object: `spec/pages/bookPage.ts` (`fillPassenger`,
  `fillContacts`, `addPassengersForm`, `submitButton`). Mock path: `spec/tests/logic/book/*`.
- **Оплата (pay)** — `/ru/f/pay`. DON'T deep-link it cold (needs booking state) and don't
  walk live by default. Preferred: the payment tests' recipe — `spec/pages/paymentPage.ts`
  (`open`, `getPaymentUrl`) + `getcheckavailresult_*` / `PAYMENT_PAGE_MOCKS` fixtures from
  `spec/mocks/responses/paymentPage/`. If walking live: fill passenger + contacts on book,
  submit, and ALWAYS carry **`?testPg=true`** (test payment gateway + test flow; real prod
  payment won't complete anyway, but always use it).
- **Заказ (order)** — `/ru/f/order?code=<ORDER_CODE>`; a real code exists only AFTER an
  order is placed. Mock path: `spec/pages/orderPage.ts` (`ORDER_PAGE_URL`) + order mocks.
  Live path: complete the test flow (search → book → pay `?testPg=true`) to mint a code,
  or take a code from the ticket.
- **Возврат — оформление (requests)** — `/ru/f/requests/<demandType>?code=…&id=…`; exact
  URL shape and params: `spec/pages/createDemandPage.ts`.
- **Возврат — просмотр (refund)** — `/ru/f/refund/<refundId>?code=<code>` (or `?key=`);
  see `spec/pages/refundPage.ts`.

**Grow this map:** after any session where you had to DISCOVER something not written here
(a step, a selector, a gotcha), save what you learned to
`.demo/<feature>/nav-notes.md` — the owner merges verified recipes back into this
map so the next run doesn't rediscover it.

## Live funnel: gotchas paid for in blood (AVIA-13257)

Only relevant when you actually walk the funnel. Mock-first is still the default.

**Booking opens in a POPUP.** The «Выбрать» button in the details modal opens a NEW TAB —
waiting for a URL change on the current page never fires. The project's own recipe is in
`spec/tests/logic/search/flightCards/flightCardChoose.spec.ts`:

    const [popup] = await Promise.all([page.waitForEvent('popup'), searchPage.flightDetails().selectButton.click()]);

**`bookPage.withPage(popup)` is not enough.** It swaps `page` but keeps the ORIGINAL
`components` (`spec/pages/bookPage.ts`), and `Select`/`Modal`/`Tooltip` resolve against
`this.page` of those components — i.e. the FIRST tab. Every select then times out with the
dropdown plainly open on screen. Build components bound to the popup and construct the page
object directly:

    new BookPage({ page: popup, components: componentsFor(popup, false), isMobile: false })

**Running the spec runner against a LIVE backend** — the auto fixtures mock things. Override
them with no-ops: `mockCommonRequests`, `mockDicts`, `mockImages`, `setBuildId`.

**The mocked suite needs a fresh prod build**: `pnpm run dicts && pnpm run build`, otherwise
`setBuildId` throws «"build_id" file not found», and rspack itself dies on missing
`src/shared/dicts/references/dicts-*.js`.

**Live inventory varies between runs** — fare labels flip between «Без багажа» and
«С багажом», prices are synthetic (a 1 млн ₽ ticket is normal on the stand). Page-object
locators tuned for mocks (`getByRole('button', {name: 'Без багажа'}).nth(1)`) do not match
live markup — prefer `flightDetails().open({flightCardNumber})`, which just clicks the card.

**On pay, the card form may not be rendered at all**: a booking can offer several payment
variants with СБП selected by default. The card block appears only after choosing
«Картой в OneTwoTrip» (`getByRole('radio', {name: /Картой в OneTwoTrip/})`).

**After «Оплатить» come upsell modals**, and their skip buttons are worded differently —
«Беру все риски на себя», «Пропустить». Loop over an alternation until none is visible.

**A `200` from `startcreateorder2` does not mean the payment succeeded.** It has its own
failure modes (see `spec/mocks/responses/paymentPage/startcreateorder2_{error,invalidEmail,
invalidParameters,session_expired}.ts`) — but it can equally answer `200 {status:"OK",
processId}` and the payment still fail afterwards. The final verdict arrives while polling
`GET /_avia/process/getprocessresult2`: `200 {status:"InProcess"}` … then `422 {error:{code}}`
(e.g. `EMPTY_CARD_HOLDER`). Read BOTH before concluding anything about a payment.
Request payload is form-encoded: `parseJsonFormData(request.postData())`.

**Test data traps** (`spec/tests/testData/passenger.ts`): `documentType` is UPPERCASE
(`'PASSPORT'`) — a lowercase value yields `length: undefined` and a one-digit document
number that the backend rejects. Do NOT pass `lang: 'ru'`: faker returns Cyrillic and the
constructor strips everything non-Latin, leaving the names empty.

**A booking expires in ~40 minutes** and is consumed by a completed payment. For repeated
runs, create the booking once, print the pay URL, and drive the payment from that URL.

**Injected demo DOM (cursor/captions) gets wiped** by the app's re-renders — re-apply it on
a `setInterval`, don't assume a single injection survives.
